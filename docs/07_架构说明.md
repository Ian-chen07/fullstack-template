# 07 架构说明

这份文档回答三个问题：项目分哪几层、一次请求怎么走、为什么这么分。

## 仓库结构

```
fullstack-template/
├── backend/                Spring Boot 后端工程
├── frontend/               Vue + Vite 前端工程
├── docs/                   需求、学习路线、自查清单、本说明
│   ├── images/             演示截图
│   └── learning/           学习过程材料（HTML 与 Java 练习），不属于交付代码
├── .agents/                会话日志（与 agent 的讨论记录）
└── README.md
```

## 后端分层

```
com.ianchen.backend
├── BackendApplication      启动类，@SpringBootApplication
├── controller/             只负责收请求、取参数、返回结果
│   ├── ApplicationController   申请相关 7 个接口
│   ├── ProjectController       项目经费
│   ├── AuthController          登录 / 退出
│   └── PingController          连通性检查
├── service/                业务规则与事务边界
│   ├── BudgetService           提交 / 批准 / 拒绝 / 取消 / 结算
│   └── AuthService             账号校验与 token 管理
├── repository/             数据库访问（Spring Data JPA 接口）
│   ├── ApplicationRepository
│   ├── ProjectRepository
│   └── UserRepository
├── entity/                 表映射
│   ├── Application
│   ├── Project
│   └── User
├── dto/                    请求体对象
│   └── CreateApplicationRequest
└── exception/              统一异常处理
    └── ApiExceptionHandler
```

各层职责：

| 层 | 干什么 | 不干什么 |
|---|---|---|
| controller | 收 HTTP 请求、拿 token 换用户、返回对象（自动转 JSON） | 不算钱、不判断业务规则 |
| service | 校验顺序、金额运算、状态流转、事务 | 不关心 HTTP、不拼 JSON |
| repository | 按条件查/存数据库 | 不写业务规则 |
| entity | 字段与表列对应 | 不放业务方法 |
| exception | 把异常变成统一的 `{status, message}` | 不处理业务 |

## 一次请求怎么走

以"老师批准 500 元"为例：

1. 浏览器点"批准" → `POST /api/applications/1/approve?amount=500`，请求头带 `X-Token`
2. Vite 开发服务器把 `/api` 代理到 8080
3. `AuthService.require(token)` 把 token 换成 `User`（查不到 → 401）
4. `ApplicationController` 调用 `BudgetService.approve(user, id, amount)`
5. `BudgetService` 按顺序校验：
   1. 角色是不是 teacher → 否则 403
   2. 是不是自己的单 → 是则 403"不能审批自己的申请"
   3. 是否同项目 → 否则 403
   4. 状态是不是 `PENDING_L1` → 否则 400
   5. 金额是否大于 0、不超过申请额、最多两位小数 → 否则 400
6. 计算差额：`差额 = 申请金额 - 批准金额`，可用加上差额、冻结减去差额，状态改 `APPROVED`
7. `projects.save()` + `applications.save()`，整个方法在 `@Transactional` 里，中途异常全部回滚
8. 返回更新后的 `Application` 对象，Spring 自动序列化成 JSON
9. 前端收到 JSON，重新拉一次列表，页面数字更新

## 数据表

| 表 | 关键列 | 说明 |
|---|---|---|
| `project` | `total_amount`、`available_amount`、`frozen_amount`、`used_amount` | 每行一个项目，四个金额始终满足"总数 = 可用 + 冻结 + 已使用" |
| `application` | `project_id`、`applicant_id`、`amount`、`approved_amount`、`actual_amount`、`status`、`reason` | 每行一张申请单 |
| `users` | `username`、`password`、`role`、`project_id` | 登录用，密码为演示明文 |

## 关键设计选择

- **为什么金额用 `BigDecimal` 且限制两位小数**：浮点数会出现 `0.1 + 0.2 ≠ 0.3`，钱不能用。
- **为什么每个写方法都加 `@Transactional`**：一次操作要改两处（项目金额 + 申请状态），必须同成同败。已用"临时抛异常"的方式验证过回滚。
- **为什么权限校验放在 service 而不是 controller**：controller 只做转发，规则集中在一处，新增接口不容易漏校验。
- **为什么 token 放内存**：演示项目不引入 Redis/JWT 依赖，重启即失效；代价是重启要重新登录。
- **为什么表结构由 `schema.sql` 管**：`ddl-auto=none`，避免 Hibernate 自动建表/删表冲掉数据。

## 已知不足

- 只支持一个项目（`project_id` 来自登录用户），没有项目切换。
- 密码明文存储，仅演示。
- 没有分页、搜索。
- token 存内存，重启后需重新登录。
